# Getting Started

This is a guide on how to get started with Cluster API Provider BringYourOwnHost(BYOH). To learn more about Cluster API in more depth, check out the [Cluster API book][cluster-api-book].

## Install Requirements
- clusterctl, which can be downloaded from the latest [release][releases] of Cluster API (CAPI) on GitHub.
- [Kind][kind] can be used  to provide an initial management cluster for testing.
- [kubectl][kubectl] is required to access your workload clusters.
- Ubuntu 20.04 and above (Linux Kernel 5.4 and above) is required for accessing kernel configs during kubeadm preflight checks.

## Create a management cluster
Cluster API requires an existing Kubernetes cluster accessible via kubectl. During the installation process the
Kubernetes cluster will be transformed into a [management cluster](https://cluster-api.sigs.k8s.io/reference/glossary.html#management-cluster) by installing the Cluster API [provider components](https://cluster-api.sigs.k8s.io/reference/glossary.html#provider-components), so it is recommended to keep it separated from any application workload.

**Choose one of the options below:**

1. **Existing Management Cluster**

    For production use-cases a "real" Kubernetes cluster should be used with appropriate backup and DR policies and procedures in place. The Kubernetes cluster must be at least greater than v1.22.x.

    ```bash
    export KUBECONFIG=<...>
    ```
**OR**

2. **Kind**

    If you are testing locally, you can use [Kind][kind] to create a cluster with the following command:

    ```shell
    kind create cluster
    ```

    The API server of this cluster listens only on `127.0.0.1` of the machine, which the hosts on other machines cannot reach. For such hosts, create the cluster with an address and a port of the machine that the hosts can reach, with `networking.apiServerAddress` and `networking.apiServerPort` (see [the configuration of kind](https://kind.sigs.k8s.io/docs/user/configuration/#api-server)):

    ```shell
    cat > kind-config.yaml <<EOF
    kind: Cluster
    apiVersion: kind.x-k8s.io/v1alpha4
    networking:
      # An address of this machine that the hosts can reach.
      apiServerAddress: "192.168.0.10"
      apiServerPort: 6443
    EOF
    kind create cluster --config kind-config.yaml
    ```

    kind strongly recommends keeping the API server on loopback for security, so choose an address that only the network of the hosts can reach, for example the address of the machine on a VPN, and do not use `0.0.0.0`. The kubeconfig of kind and the bootstrap kubeconfigs created below then point to this address.

---
[kind] is not designed for production use.

**Minimum [kind] supported version**: v0.9.0

Note for macOS users: you may need to [increase the memory available](https://docs.docker.com/docker-for-mac/#resources) for containers (recommend 6Gb for CAPD).

---

## Initialize the management cluster and install the BringYourOwnHost provider

Now that we've got clusterctl installed and all the prerequisites in place, let's transform the Kubernetes cluster
into a management cluster by using `clusterctl init`.

The `byoh` provider built into clusterctl points to the upstream repository, vmware-tanzu/cluster-api-provider-bringyourownhost. To install the provider from this repository, override it in the clusterctl configuration file (by default `~/.config/cluster-api/clusterctl.yaml`; see [provider repositories](https://cluster-api.sigs.k8s.io/clusterctl/configuration.html#provider-repositories)):

```yaml
providers:
- name: byoh
  url: https://github.com/superbrothers/cluster-api-provider-bringyourownhost/releases/latest/infrastructure-components.yaml
  type: InfrastructureProvider
```

```shell
clusterctl init --infrastructure byoh
```
Note: By default, CSRs generated by BYOH host agents are automatically approved during registration. If we want to disable automatic approval, then set variable `MANUAL_CSR_APPROVAL: "enable"` in clusterctl config file. Reference for setting variables in clusterctl can be found [here](https://cluster-api.sigs.k8s.io/clusterctl/configuration.html#variables).

## Creating a BYOH workload cluster
 
Once the management cluster is ready, you will need to create a few hosts that the `BringYourOwnHost` provider can use, before you can create your first workload cluster.

If you already have hosts (these could be bare metal servers / VMs / containers) ready, then please skip to [Register BYOH host to management cluster](#register-byoh-host-to-management-cluster)

If not, you could create containers to deploy your workload clusters on. We have a `make` task that will create a docker image for you locally to start. 

```shell
cd cluster-api-provider-bringyourownhost
make prepare-byoh-docker-host-image
```

If you are using dev environment, you could use below target that creates docker image with all k8s components installed.

```shell
cd cluster-api-provider-bringyourownhost
make prepare-byoh-docker-host-image-dev
```

Once the image is ready, lets start 2 docker containers for our deployment. One for the control plane, and one for the worker. (you could of course run more)

```shell
for i in {1..2}
do
  echo "Creating docker container named host$i"
  docker run --detach --tty --hostname host$i --name host$i --privileged --security-opt seccomp=unconfined --tmpfs /tmp --tmpfs /run --volume /var --volume /lib/modules:/lib/modules:ro --network kind byoh/node:e2e
done
```

## Register BYOH host to management cluster


### Generating the Bootstrap Kubeconfig file
Get the APIServer and Certificate Authority Data info

```shell
APISERVER=$(kubectl config view -ojsonpath='{.clusters[0].cluster.server}')
CA_CERT=$(kubectl config view --flatten -ojsonpath='{.clusters[0].cluster.certificate-authority-data}')
```

Each host needs its own bootstrap kubeconfig, and it must be used within 30 minutes, as the bootstrap token in it expires then. See [Host registration and permissions](host_registration.md) for how the hosts join the management cluster and what they can do there.

Create a BootstrapKubeconfig CR for each host (2 for this guide) as follows
```shell
for i in {1..2}
do
cat <<EOF | kubectl apply -f -
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: BootstrapKubeconfig
metadata:
  name: bootstrap-kubeconfig-host$i
  namespace: default
spec:
  apiserver: "$APISERVER"
  certificate-authority-data: "$CA_CERT"
EOF
done
```

Once the BootstrapKubeconfig CRs are created, fetch the bootstrap kubeconfig files from their Status field
```shell
for i in {1..2}
do
kubectl get bootstrapkubeconfig bootstrap-kubeconfig-host$i -n default -o=jsonpath='{.status.bootstrapKubeconfigData}' > ~/bootstrap-kubeconfig-host$i.conf
done
```

---
### VM Prerequisites
- The following packages must be pre-installed on the VMs
  - socat
  - ebtables
  - ethtool
  - conntrack
- You can install these with
``` shell
sudo apt-get install socat ebtables ethtool conntrack
```
- The output of `hostname` should be added to `/etc/hosts`

Example:
```shell
$ hostname
node01

$ cat /etc/hosts
127.0.0.1 localhost
127.0.0.1 node01
...
```
- The hostname of each host must be unique in the management cluster, and must be a lowercase DNS subdomain. It becomes the name of the ByoHost and the common name of the certificate of the host (see [Host registration and permissions](host_registration.md)), and a host with the hostname of another host takes over its ByoHost. Some images, such as Ubuntu for Raspberry Pi, name every host `ubuntu`. Set a hostname before you start the agent, for example:
```shell
sudo hostnamectl set-hostname node01
```
- The clock of the host must be synchronized, as the agent connects to the management cluster with TLS. The agent starts after `time-sync.target`, which does not wait for the synchronization by default. On the hosts without a real-time clock, such as Raspberry Pi, enable the service that waits for it: `chrony-wait.service` with chrony (the default of Ubuntu 25.10 and later), or `systemd-time-wait-sync.service` with systemd-timesyncd (the default of Ubuntu 24.04).
```shell
sudo systemctl enable chrony-wait.service
```

### Installing the agent on your hosts

If you are trying this on your own hosts, install the agent from the deb package of the release on each host. The package runs the agent as the systemd service `byoh-hostagent`.

1. Download the package of the architecture of the host, and check it with `checksums.txt` of the release, which has the SHA-256 of all the assets of the release:
    ```shell
    curl -fLO https://github.com/superbrothers/cluster-api-provider-bringyourownhost/releases/download/v0.6.0/byoh-hostagent_0.6.0_$(dpkg --print-architecture).deb
    curl -fLO https://github.com/superbrothers/cluster-api-provider-bringyourownhost/releases/download/v0.6.0/checksums.txt
    sha256sum --check --ignore-missing checksums.txt
    ```
    When it prints `OK` for the package, install the package:
    ```shell
    sudo apt install ./byoh-hostagent_0.6.0_$(dpkg --print-architecture).deb
    ```
    Installing the package does not start the agent.
2. Copy the bootstrap kubeconfig of the host (for example `~/bootstrap-kubeconfig-host1.conf`) only to that host, and put it where the service reads it:
    ```shell
    sudo install -m 0600 bootstrap-kubeconfig-host1.conf /etc/byoh-hostagent/bootstrap-kubeconfig
    ```
3. Set the flags of the agent in `BYOH_HOSTAGENT_ARGS` of `/etc/default/byoh-hostagent` with `sudoedit /etc/default/byoh-hostagent`. Set the label of the role of the host: `role=control-plane` for the control plane, and `role=worker` for the workers. The cluster templates select the hosts by this label. Register the host in the namespace of the cluster, as a ByoMachine selects only the ByoHosts in its own namespace: add `--namespace=<namespace>` when the cluster is not in `default`. See [BYOH agent](byoh_agent.md) for the flags.
    ```shell
    BYOH_HOSTAGENT_ARGS="--label=role=control-plane"
    ```
4. Start the agent, and enable it to start at boot:
    ```shell
    sudo systemctl enable --now byoh-hostagent
    ```
5. Check that it runs, and see its log:
    ```shell
    systemctl status byoh-hostagent
    journalctl -u byoh-hostagent -f
    ```

After the host is registered (see `kubectl get byohosts` below), remove the bootstrap kubeconfig from the host. The agent then uses the kubeconfig of the host in `/root/.byoh/config`.

```shell
sudo rm /etc/byoh-hostagent/bootstrap-kubeconfig
```

---
If you are trying this using the docker containers we started above, then we would first need to prep the kubeconfig to be used from the docker containers. By default, the kubeconfig states that the server is at `127.0.0.1`. We need to swap this out with the kind container IP. 

```shell
export KIND_IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' kind-control-plane)
sed -i 's/    server\:.*/    server\: https\:\/\/'"$KIND_IP"'\:6443/g' ~/bootstrap-kubeconfig-host*.conf
```
Download the binary of the agent of the release into your working directory, and check it with `checksums.txt` of the release:

```shell
curl -fLO https://github.com/superbrothers/cluster-api-provider-bringyourownhost/releases/download/v0.6.0/byoh-hostagent-linux-amd64
curl -fLO https://github.com/superbrothers/cluster-api-provider-bringyourownhost/releases/download/v0.6.0/checksums.txt
sha256sum --check --ignore-missing checksums.txt
```

When it prints `OK` for the binary, use the following script to copy it to the containers.

```shell
for i in {1..2}
do
echo "Copy agent binary to host $i"
docker cp byoh-hostagent-linux-amd64 host$i:/byoh-hostagent
echo "Copy kubeconfig to host $i"
docker cp ~/bootstrap-kubeconfig-host$i.conf host$i:/bootstrap-kubeconfig.conf
done
```

Start host agent on each of the hosts from root user and keep it running. Label `host1` with `role=control-plane` and `host2` with `role=worker`, as the cluster templates select the hosts by the label of the role.

>**IMPORTANT NOTE**: Use the `--skip-installation` flag if using target `make prepare-byoh-docker-host-image-dev` as we already have k8s components included in this docker image. This flag will skip k8s installation attempt on the host. The `--skip-installation` flag should not be used with target `make prepare-byoh-docker-host-image` as it's docker image doesn't come with k8s components installed.

```shell
export HOST_NAME=host1
docker exec -it $HOST_NAME sh -c "chmod +x byoh-hostagent && ./byoh-hostagent --bootstrap-kubeconfig bootstrap-kubeconfig.conf --label role=control-plane"

# do the same for host2 in a separate tab
export HOST_NAME=host2
docker exec -it $HOST_NAME sh -c "chmod +x byoh-hostagent && ./byoh-hostagent --bootstrap-kubeconfig bootstrap-kubeconfig.conf --label role=worker"
```

```shell
kubectl get byohosts
```

## Create workload cluster
Running the following command(on the host where you execute `clusterctl` in previous steps)

**NOTE:** The `CONTROL_PLANE_ENDPOINT_IP` is the address of the load balancer in front of the API servers of the control plane. BYOH does not provide the load balancer, so prepare one for your environment. When the control plane has only one machine, you can use the IP of that host instead. `CONTROL_PLANE_ENDPOINT_PORT` sets the port of the endpoint (default `6443`).

If you are using docker containers with one control plane machine, use the IP of `host1`, which is labeled with `role=control-plane`:

```shell
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' host1
```

The cluster templates update the machines without a spare host: the MachineDeployment uses `maxSurge: 0`. The control plane uses `CONTROL_PLANE_MAX_SURGE` (default `1`), which needs a spare host labeled with `role=control-plane`. Set it to `0` to update the control plane without a spare host, which needs 3 or more control plane machines.

### Create the workload cluster
Generate the cluster.yaml for workload cluster
 - for vms as byohosts
    ```shell
    CONTROL_PLANE_ENDPOINT_IP=10.10.10.10 clusterctl generate cluster byoh-cluster \
      --infrastructure byoh \
      --kubernetes-version v1.26.6 \
      --control-plane-machine-count 1 \
      --worker-machine-count 1 > cluster.yaml
    ```

 - for docker hosts use the --flavor argument
    ```shell
    CONTROL_PLANE_ENDPOINT_IP=10.10.10.10 clusterctl generate cluster byoh-cluster \
        --infrastructure byoh \
        --kubernetes-version v1.26.6 \
        --control-plane-machine-count 1 \
        --worker-machine-count 1 \
        --flavor docker > cluster.yaml
    ```

Inspect and make any changes
```shell
vi cluster.yaml
```

Create the workload cluster in the current namespace on the management cluster
```shell
kubectl apply -f cluster.yaml
```

## Accessing the workload cluster

The `kubeconfig` for the workload cluster will be stored in a secret, which can
be retrieved using:

``` shell
kubectl get secret/byoh-cluster-kubeconfig -o json \
  | jq -r .data.value \
  | base64 --decode \
  > ./byoh-cluster.kubeconfig
```

The kubeconfig can then be used to install a CNI for networking, for example, Calico (https://docs.tigera.io/calico/latest/getting-started/kubernetes/self-managed-onprem/onpremises). The cluster templates use `192.168.0.0/16` for the pods.

after that you should see your nodes turn into ready:

```shell
$ KUBECONFIG=byoh-cluster.kubeconfig kubectl get nodes
NAME                                                          STATUS     ROLES    AGE   VERSION
byoh-cluster-8siai8                                           Ready      master   5m   v1.26.6
```

## Managing the agent on your hosts

The package `byoh-hostagent` installs:

- `/usr/bin/byoh-hostagent`, the agent;
- `/usr/lib/systemd/system/byoh-hostagent.service`, which runs the agent as root with `--bootstrap-kubeconfig=/etc/byoh-hostagent/bootstrap-kubeconfig` and the flags in `BYOH_HOSTAGENT_ARGS`, and restarts it whenever it exits. The service starts only when `/etc/byoh-hostagent/bootstrap-kubeconfig` or `/root/.byoh/config` exists;
- `/etc/default/byoh-hostagent`, which sets `BYOH_HOSTAGENT_ARGS`;
- `/etc/byoh-hostagent/` (mode 0700), for the bootstrap kubeconfig of the host.

The agent keeps the kubeconfig of the host, with its certificate and private key, in `/root/.byoh/config`, and its temporary files in `/var/lib/byoh-hostagent`.

### Changing the flags

Edit `/etc/default/byoh-hostagent`, and restart the agent:

```shell
sudo systemctl restart byoh-hostagent
```

The agent sets the labels of `--label` only when it creates the ByoHost, so changing them does not change the labels of a registered host.

### Upgrading the agent

Install the package of the new release over the old one. Use the agent of the same release as the provider. Download the package and check it with `checksums.txt` of the release:

```shell
curl -fLO https://github.com/superbrothers/cluster-api-provider-bringyourownhost/releases/download/<version>/byoh-hostagent_<version without v>_$(dpkg --print-architecture).deb
curl -fLO https://github.com/superbrothers/cluster-api-provider-bringyourownhost/releases/download/<version>/checksums.txt
sha256sum --check --ignore-missing checksums.txt
```

When it prints `OK` for the package, install the package:

```shell
sudo apt install ./byoh-hostagent_<version without v>_$(dpkg --print-architecture).deb
```

The upgrade restarts the agent if it is running. Do not upgrade the agent while its host is being provisioned or deleted, that is, while the Machine of the host is being created or deleted: the restart stops the installation script or kubeadm that the agent is running.

The agent reports its version to its ByoHost every time it starts, so the column `AGENTVERSION` of `kubectl get byohosts` shows the version that each host runs.

### Stopping and removing the agent

Stopping or removing the agent does not reset the host: the kubelet and the node keep running. To take a host out of a cluster, delete or scale down its Machine first, and wait until the agent resets the host and its ByoHost is no longer attached to a Machine.

- To stop the agent: `sudo systemctl disable --now byoh-hostagent`.
- To remove the agent: `sudo apt remove byoh-hostagent`. This stops the agent, and keeps `/etc/default/byoh-hostagent`, the bootstrap kubeconfig if it is there, and `/root/.byoh/config`, so that the host can run the agent again with the same identity.
- To remove the agent and its data: `sudo apt purge byoh-hostagent`. This also removes `/etc/default/byoh-hostagent`, `/etc/byoh-hostagent`, `/var/lib/byoh-hostagent`, and `/root/.byoh` with the kubeconfig and the private key of the host. The host has to be registered again with a new bootstrap kubeconfig to run the agent again. When you remove the host for good, also delete its ByoHost (see [Operating securely](host_registration.md#operating-securely)).
